# ДЗ 3: прогноз покупок клиента за 30 дней

Стартовые бейзлайны для [HW3 ML MIPT autumn 2026](https://www.kaggle.com/competitions/hw-3-ml-mipt-autumn-2026). Цель — `spend_30d`, метрика — RMSLE.

## Бейзлайны

| Имя | Подход | Фиксированные настройки |
|---|---|---|
| `logmean` | Среднее `log1p` сумм шести предыдущих 30-дневных окон, включая нулевые | Без обучения |
| `ridge` | Линейная регрессия с L2 на `log1p(spend_30d)` | `alpha=10` |
| `forest` | Случайный лес на `log1p(spend_30d)` | 200 деревьев, глубина 12, минимум 20 строк в листе |
| `mlp` | Полносвязная сеть на `log1p(spend_30d)` | Скрытые слои 128/64, ReLU, Adam, 60 эпох |

Модели выбраны вручную. Настройки находятся в `configs/baselines.json`; автоматического поиска алгоритмов, архитектур или гиперпараметров нет. Бустинги, AutoML и внешние данные не используются.

## Данные

Скачайте четыре исходных CSV с вкладки Data соревнования и положите их в `data/raw/`:

```text
data/raw/transactions.csv
data/raw/train.csv
data/raw/test.csv
data/raw/sample_submission.csv
```

Данные, признаки отдельных клиентов, веса и файлы предсказаний исключены из Git. Репозиторий содержит код и агрегированные результаты.

Очистка удаляет точные повторы строк, операции без известного клиента, отмены с префиксом `R`, неположительные количества/цены, `SVC00`–`SVC13` и позиции с префиксом `GFT`. Товарные покупки агрегируются по клиенту и дате. При запуске восстанавливаются **все известные train-ответы**; расхождение больше 0,011 УЕ останавливает расчёт.

## Установка и запуск на CPU

Рекомендуется Python 3.12. Команды выполняются из корня репозитория.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[neural]'
python -m unittest discover -s tests -v
python -m spend_baselines validate --models logmean ridge forest mlp --device cpu --threads 2
```

Без установки PyTorch доступны первые три модели:

```bash
python -m pip install -e .
python -m spend_baselines validate --models logmean ridge forest
```

Метрики сохраняются в `outputs/baselines/scores.csv`, конфигурация, версии и SHA256 исходников — в `run_manifest.json`. Также сохраняются локальные прогнозы и кривая обучения MLP. Параметр `--epochs 2` позволяет явно запросить короткий пробный запуск; он записывается в манифест.

## Запуск MLP на V100

Для Linux-сервера с V100 предусмотрен явный выбор CUDA. В отдельном окружении Python 3.12:

```bash
python -m pip install -e .
python -m pip install torch==2.5.1 --index-url https://download.pytorch.org/whl/cu121
python -m spend_baselines validate --models mlp --device cuda --threads 2 --out-dir outputs/mlp-v100
```

Команда установки соответствует [официальной инструкции PyTorch 2.5.1](https://pytorch.org/get-started/previous-versions/#v251). GPU-запуск должен выполняться на машине с доступным CUDA-устройством. Если CUDA недоступна, команда завершится с явной ошибкой.

## Регуляризация MLP, ранняя остановка и разные seed

Три заранее заданных варианта: исходная регуляризация, усиленный L2 и dropout 10%. Каждый повторяется с seed 42, 123 и 2026 на двух внешних датах. Это 18 отдельных оценок; автоматический выбор конфигурации не выполняется.

```bash
python -u -m spend_baselines mlp-experiment \
  --device cuda --threads 2 \
  --out-dir outputs/mlp-regularization --resume
```

Для сентября число эпох выбирается по внутренней проверке на августе; для октября — по сентябрю. После выбора сеть заново обучается на всех доступных для внешней даты строках. Подробный протокол, параметры, файлы результатов и короткий CPU-запуск: [docs/mlp-experiments.md](docs/mlp-experiments.md).

## Временная проверка

- Проверочные даты: **1 сентября и 1 октября 2018**.
- В обучение каждой проверки попадают только строки с `target_end <= validation_date`.
- Каждый признак использует операции **строго до `as_of_date` своего объекта**.
- Заполнение пропусков и масштабирование обучаются только на обучающей части.
- ID клиента служит связыванию таблиц и не является числовым признаком.
- В исходном `validate` MLP обучается фиксированное число эпох. В `mlp-experiment` ранняя остановка использует отдельную внутреннюю временную проверку; внешняя дата не участвует в выборе эпох.
- Локальные RMSLE нельзя напрямую сравнивать с public leaderboard на другом наборе объектов.

Основные признаки: давность покупки, длина истории, число покупательских дней и суммы за 30/60/90/180 дней, последняя/средняя/медианная сумма, месяц. С помощью `--features extended` можно вручную проверить добавку ритма, дня недели, часов и вариативности сумм. Это отдельная проверяемая гипотеза.

## Локальный файл для Kaggle

После выбора модели по проверке:

```bash
python -m spend_baselines submit --model ridge --out-dir outputs/submission
```

Будет создан CSV с колонками `Id,spend_30d`, порядком строк из `sample_submission.csv` и конечными неотрицательными суммами в исходных УЕ. Обратное преобразование `expm1` выполняется в коде. Команда **не отправляет** файл в Kaggle.

## Полный набор экспериментов на V100

Новая команда `python -m spend_baselines.suite` сохраняет исходные команды выше.
Конфиги задают ручные сравнения; автоматического поиска или выбора лучшего
алгоритма/seed нет. Kaggle upload отсутствует.

| Конфиг | Оценок на пяти внешних датах | Назначение |
|---|---:|---|
| `configs/v100_suite.json` | 515 | Целевые сравнения: контроль дат/признаков, сложные модели на D2/F2, последовательные сети, ограниченный бэггинг |
| `configs/full_suite.json` | 49 880 | Полное произведение D0–D3, F0–F4, четырёх последовательных входов, шести профилей/трёх seed, ансамблей до 32 сетей |

Оценка нейросети включает **два обучения**: выбор эпох на внутренней дате и
повторный fit с нуля на всех доступных метках. Это соответственно 840 и
97920 нейросетевых fit. Дополнительные сочетания готовых прогнозов не требуют
повторного обучения компонент.

Основной конфиг перечисляет `experiments` отдельными блоками, а не перемножает
все таблицы и модели. Совпадающие fit между блоками выполняются один раз.

- Ridge, лес и одна MLP сравнивают D0/F0, D2/F0, D0/F2, D2/F1 и D2/F2:
  дополнительные даты, короткая активность, корзина и их взаимодействие.
- Сплайны, hurdle-компоненты, Wide/residual MLP и ZILN проверяются на D2/F2.
  Для содержательных нейросетевых сравнений используются три фиксированных
  seed; ширина и dropout сравниваются только у обычной MLP.
- Плоская MLP, TCN, GRU и LSTM получают одинаковый S1+F2. S0+F0 оставлен
  контролем представления только у плоской MLP; двухчастный выход у ряда
  проверяется на GRU.
- Для обычной и двухчастной MLP сравниваются по 8 seed-сетей и по 8
  customer-bootstrap сетей при одинаковой архитектуре и числе участников. Wide/residual и случайное исключение
  блоков признаков в этот этап не включены.
- BG/NBD и Pareto/NBD с Gamma-Gamma используют всю доступную историю.
  D3, F3, F4 и обрезанная до 180 дней CLV-история оставлены за основным прогоном.

Из корня клона, с четырьмя исходными CSV в `data/raw/`, Python 3.11/3.12 и
рабочим PyTorch/CUDA:

```bash
python -m pip install -e '.[neural]'
bash scripts/run_v100_suite.sh configs/v100_suite.json outputs/v100-focused
```

Архивный конфиг полного декартова произведения доступен для воспроизведения; в основной прогон он не входит:

```bash
bash scripts/run_v100_suite.sh configs/full_suite.json outputs/full-suite
```

Скрипт проверяет CUDA, печатает точное число заданий, пишет `console.log` и
продолжает прерванный идентичный запуск. Встроенный блокировщик запрещает два
обучающих процесса в одном output-каталоге. Один процесс последовательно
обучает модели на GPU, леса/CLV — на CPU с двумя потоками. Данные, код, конфиг,
версии библиотек, устройство и число потоков закреплены в манифесте; при их
изменении требуется другой output-каталог. Незавершённое задание начинается
заново, завершённое пропускается только после сверки SHA256 всех артефактов.
Веса внутри незавершённой эпохи не восстанавливаются.

При низкой загрузке V100 можно продолжить тот же прогон двумя независимыми
процессами. Сначала остановите последовательный запуск через Ctrl+C, затем:

```bash
git pull --ff-only
bash scripts/run_v100_parallel.sh 2
```

Используется тот же `outputs/v100-focused`. Существующие готовые задания
проверяются по SHA256 и пропускаются, текущее незавершённое задание начинается
заново. Каждый процесс имеет независимое состояние seed; batch size, точность,
алгоритм и эпохи не меняются. Код моделей и исходный манифест остаются прежними;
SHA запускатора и число процессов записываются отдельно в технические метаданные.
Блокировка запрещает пересечение с последовательным или вторым параллельным
запуском в том же каталоге. Математический код в `src/spend_baselines/` при
переходе не изменяется, поэтому завершённые результаты можно переиспользовать.

`parallel-console.log` содержит завершения заданий, `parallel_logs/<job_id>.log`
— подробные эпохи конкретного задания. GPU-память и CPU/RAM нужны каждому
процессу. Начальный вариант — два процесса; четыре можно попробовать отдельным
запуском `bash scripts/run_v100_parallel.sh 4`, сравнивая задания в минуту и
использование памяти. Рост процента GPU сам по себе не доказывает ускорение.
Ускорение на V100 нужно измерить на сервере; локальные проверки сравнивают
результаты параллельного и последовательного CPU-обучения.

Подготовку данных можно выполнить отдельно:

```bash
python -m spend_baselines.suite prepare --config configs/v100_suite.json --out-dir outputs/v100-focused
```

### Данные и временные границы

- **D0**: исходные месячные строки; **D1**: срезы 1/8/15/22; **D2**: D1 с
  одинаковым общим весом каждого клиент–месяца; **D3**: ежедневные срезы с теми
  же весами. Веса считаются после каждой временной отсечки.
- В дополнительных срезах сохраняется условие покупки за прошлые 180 суток.
  Все первоначальные train-строки и ответы сверяются. Ответы синтетических
  строк восстанавливаются только в полностью наблюдаемом 30-дневном окне.
- **F0**: прежние 15 RFM; **F1**: короткая активность и динамика; **F2**:
  корзина/товары/возвраты/регион; **F3**: также регулярность; **F4**: F2 и
  причинно по времени вычисленные признаки BG/NBD/Pareto-NBD/Gamma-Gamma.
  Регион кодируется восемью стабильными hash-индикаторами, без внешних данных.
- **S0/S1**: 26 недель × 2/6 покупательских каналов плюс coverage-канал;
  **S0_F0/S1_F2** также получают табличные признаки. Недели идут от старых к
  новым. Возвраты — отдельные признаки и не меняют положительный target.
- Внешние даты: июнь–октябрь 2018. Проверяются только официальные месячные
  объекты; inner validation — последняя месячная дата с уже доступными ответами. Train содержит
  только `target_end <= cutoff`. Масштабирование/импутация обучаются на train.
  Сентябрь/октябрь ранее использовались для принятия решений; это не новый
  независимый holdout.

### Модели и результаты

Реализованы Ridge, лес, сплайны, обычная/Wide/residual MLP, две совместные
hurdle-сети, ZILN, TCN, GRU, LSTM, BG/NBD и Pareto/NBD с Gamma-Gamma. Для CLV
начало наблюдения — первый наблюдавшийся заказ в выбранном окне, не доказанная
дата привлечения клиента. Непрерывные likelihood и положительные параметры
оцениваются численно; сходимость интеграла Pareto сверяется двойным числом
узлов. Для RMSLE из CLV/ZILN берётся `E[log1p(Y)]`, а не `log1p(E[Y])`.
CLV-диагностика хранит стандартную ошибку Monte Carlo; неопределённость
параметров не интегрируется. F4 готовится по датам с возобновляемыми shards.

Отдельные классификаторы/положительные регрессоры дают 16 hurdle-сочетаний.
Для вероятностей сохраняются Brier/AUC; положительные компоненты оцениваются
на положительных целях. У сетей с purchase-head также сохраняются вероятности.
Все полноценные модели оцениваются общей RMSLE и на нулевых/положительных целях.
В `derived_scores.csv` лежат заранее заданные ансамбли, hurdle-комбинации,
hard gate 0.5, временной Ridge-stacking и softmax-роутер. Последние обучаются
только на более ранних OOT-прогнозах с уже доступными ответами.

`scores.csv` обновляется каждые 25 посещённых заданий. После завершения команды
`status.json` показывает число фактически готовых и оставшихся заданий,
`pooled_scores.csv`/`derived_pooled.csv` — RMSLE из сумм квадратов, `jobs/` —
точные прогнозы, веса, кривые, параметры и контрольные суммы. Ошибки не
считаются успешными заданиями: сохраняется `error.json`, выполнение остальных
заданий продолжается, процесс в конце возвращает ненулевой код. Результаты
частичных запусков всегда содержат фактическое число проверочных дат.

Собрать имеющиеся результаты повторно или запустить часть плана:

```bash
python -m spend_baselines.suite combine --config configs/v100_suite.json --out-dir outputs/v100-focused --device cuda
python -m spend_baselines.suite run --config configs/full_suite.json --out-dir outputs/full-suite --device cuda --resume --datasets D0 --representations F0 --kinds tabular neural
```

Для выбранного **самостоятельного** предиктора `job_id` из `scores.csv`:

```bash
python -m spend_baselines.suite refit --config configs/v100_suite.json --out-dir outputs/v100-focused --device cuda --resume --job-ids JOB_ID
```

Команда выберет эпохи на октябре, переобучит на всех метках до тестовой даты и
создаст локальный `submission.csv`. Чистые probability/positive-компоненты
не выдаются за самостоятельные прогнозы трат.

Производный кандидат выбирается по имени из `derived_scores.csv`. Например,
переобучить hurdle из логистической вероятности и положительного леса:

```bash
python -m spend_baselines.suite refit --config configs/v100_suite.json --out-dir outputs/v100-focused --device cuda --resume --datasets D2 --representations F2 --candidate 'hurdle:linear+forest'
```

Аналогично доступны имена `equal_linear_forest`, `oot_soft_router`,
`oot_stack_ridge` и `ensemble:customer:mlp:direct:n8`. Компоненты и участники
переобучаются на данных до тестовой даты; метапредиктор использует доступные
исторические OOT-ответы. Порядок submission сверяется с sample submission.

Короткая сквозная CPU-проверка всех семейств, с 64 клиентами, одной небольшой
архитектурой и максимум двумя эпохами:

```bash
python -m unittest discover -s tests -v
python -m spend_baselines.suite run --smoke --device cpu --out-dir outputs/suite-smoke --resume
```

Smoke — проверка реализации, его метрики не являются оценкой качества полного
обучения. CUDA/V100 проверяются на машине запуска. Методические первичные
источники: [BG/NBD](https://www.brucehardie.com/notes/004/),
[Pareto/NBD](https://www.brucehardie.com/notes/009/),
[Gamma-Gamma](https://www.brucehardie.com/notes/025/),
[ZILN](https://arxiv.org/abs/1912.07753).
