# Товарные эмбеддинги + Joint MLP

Этап после проверки `history-tuning-results.tar.gz`. HP-подбор завершён:
39 seed-оценок, 78 fit, 179 экспортированных SHA проверены, максимум ошибки
воспроизведения метрик/CI — 5.05e-16. Ранний отбор выбрал `lr_double`, но его
улучшение не подтвердилось на поздних датах:

| Профиль mean3 | June–August | September | October | Pooled Sep–Oct |
|---|---:|---:|---:|---:|
| Текущий Joint+history, lr=0.001 | 2.375486 | 2.602955 | 2.645138 | **2.624691** |
| lr_double, lr=0.002 | **2.363813** | 2.603526 | 2.648582 | 2.626749 |

Разница подтверждения +0.002058, customer-bootstrap 95% CI
[−0.002250; +0.006622]. Это отсутствие подтверждённого улучшения;
статистически доказанным ухудшением результат не объявляется. Для нового
эксперимента сохраняются исходные lr=0.001, L2=0.0001, dropout=0, batch=1024.
Dropout0.05 проходил mean3 только на ранних датах; по протоколу на подтверждение
пошёл только победитель. Прирост pooled5 у lr_double относится также к датам
подбора и не заменяет позднюю проверку. Три диагностические фиксированные
смеси с lr_double дали менее0.00034 выигрыша и CI с нулём; они не приняты.

Все агрегаты: `docs/history-tuning-cuda-scores.csv`.

## Новая гипотеза

Проверяется цепочка:

```text
item_id из прошлого клиента → обучаемые векторы → взвешенная сумма
                                                    ↓
                         F2 + causal history → Joint MLP 128/64 → p × mu+
```

Это обучаемые end-to-end товарные эмбеддинги. Среднее, доля нулей, EWMA и
count известных прошлых меток остаются прежними. Добавления customer_id
как входного признака, трансформера или графовой сети нет.

Рассматриваются только два размера embedding: **16 и 32**. База, даты,
loss `hurdle_joint`, Adam, три seed42/123/2026 и preprocessing прежние.
Параметры товарной ветки фиксированы, без нового HP-перебора.

Для суммирования используется `torch.nn.EmbeddingBag(mode='sum')` с весами
покупок; эта операция объединяет набор товаров без создания отдельного
тензора всех embedding-векторов. Источники метода:
[PyTorch 2.5.1 sparse modules](https://github.com/pytorch/pytorch/blob/v2.5.1/torch/nn/modules/sparse.py)
и [Deep Sets](https://arxiv.org/abs/1703.06114). Используются только внутренние
транзакции соревнования; внешнего предобучения или внешних данных нет.

## Точная спецификация

* Берутся только положительные товарные покупки по прежнему контракту очистки.
  Отмены, возвраты, сервисные и подарочные позиции не входят в item bags.
* Для строки на t история — `[t−180 дней, t)`. Один товар в один покупательский
  день даёт одно событие; большое число строк/количество единиц в одном дне
  не увеличивает его массу. Веса событий равны `2**(−age_days/90)`.
* События одного товара суммируются. Сохраняются top128 товаров по массе,
  равенства разрешаются по имени товара. Веса оставшихся товаров нормируются
  к сумме1. Для очень больших историй сохраняется доля массы, прошедшей cap.
* Кэш содержит только числовые коды/веса. Само наличие имени в словаре
  сырых кодов не создаёт обучаемый embedding.
* **Обучаемый словарь строится отдельно для inner train и outer train.**
  Используются только bags строк, прошедших `target_end <= cutoff`.
  Товару требуется поддержка минимум3 различных клиентов; повторные даты
  одного клиента не размножают support. Поздние и редкие товары имеют ID0
  с фиксированным нулевым вектором. Пустая/полностью неизвестная история
  также даёт нулевой товарный вектор.
* Inner selection и outer refit обучают embedding-таблицу с нуля, вместе
  с MLP. Outer не наследует таблицу/веса inner. Выбранная эпоха определяется
  только более ранней внутренней датой по прежнему правилу.
* Новая таблица инициализируется N(0,0.05²); для неё L2=0.001.
  Остальные параметры сохраняют L2=0.0001. Вычисления float32, без AMP;
  deterministic algorithms включены, как у исходной модели.

Тесты проверяют будущие/пограничные события, смену числовых кодов после
добавления будущего товара, отсутствие будущего товара в обучаемом словаре,
support по клиентам, инвариантность пулинга к порядку, ненулевые градиенты,
нулевой padding, неизвестные товары и переносимые checkpoints.

## Запуск на V100

Тот же исходный `outputs/behavior-v1` служит источником контроля и истории.
Результат HP-подбора `lr_double` не становится новым default.

```bash
git switch codex/full-experiment-suite
git pull --ff-only
python -m pip install -e .
bash scripts/run_item_embeddings_v100.sh
```

Максимум30 новых seed-оценок /60 fit на June–October. Контроль не обучается
повторно. Подготовка предметных bags работает на CPU; новые сети — на CUDA.
Предыдущие OOF/history-признаки переиспользуются без повторных Ridge-fit.

Скрипт пишет в новый `outputs/item-embeddings-v1`, ограничен90минутами между
seed-оценками и поддерживает `--resume`. Повтор той же команды продолжает
незавершённый запуск. Если лимит остановил прогон, `status.json` содержит
`phase_complete=false`; неполный прогон не считается подтверждением модели.

После выполнения создаётся **`item-embeddings-results.tar.gz`** — скачайте и
пришлите его. Архив содержит прогнозы, средние трёх seed, кривые, параметры,
поддержку словаря/долю известной массы, времена, метрики и контрольные суммы.
Feature caches и веса остаются на сервере. `zip` не требуется.

Для следующего snapshot существующего output-каталога используйте новое имя:

```bash
python -m spend_embeddings export --out-dir outputs/item-embeddings-v1 --archive item-embeddings-results-2.tar.gz
```

Второй/третий/четвёртый аргументы запускают другой output, имя архива и лимит:

```bash
bash scripts/run_item_embeddings_v100.sh outputs/behavior-v1 outputs/item-embeddings-v1 item-embeddings-results-2.tar.gz 90
```

Скачанный `behavior-results.tar.gz` тоже можно использовать как reference;
тогда F2 cache указывается через `--base-cache`:

```bash
python -m spend_embeddings run --reference behavior-results.tar.gz \
  --base-cache outputs/v100-focused/cache --out-dir outputs/item-embeddings-v1 \
  --device cuda --threads 2 --resume
```

## Оценка и возможный рефит

`scores.csv` содержит даты, pooled Sep–Oct и pooled5 при наличии всех дат,
delta/2000-repeat customer-cluster bootstrap CI к контролю2.624691.
`error_slices.csv` показывает нулевые/положительные ответы и группы0/1–2/3+
покупательских дней. Проверяются также фиксированные смеси с контролем:
90/10,75/25,50/50 в log1p, без оптимизации весов.

`timing.csv` и job records содержат fit/inference time, размер словаря,
долю известной товарной массы на проверке и долю массы после top128 cap.
Все seed-прогнозы сохраняются построчно для независимого пересчёта.
Нельзя считать словарный размер или использование embedding доказательством
улучшения RMSLE. Внешние даты уже использовались; CI условные, без поправок
на выбор модели/множественные сравнения/drift. November test ещё не измерен.

После анализа результатов можно явно рефитить выбранный вариант:

```bash
python -m spend_embeddings refit --profile item16 --reference outputs/behavior-v1 \
  --out-dir outputs/item-embeddings-v1 --device cuda --threads 2 --resume
```

Результат этой команды — веса, словарь, preprocessing и NPZ с усреднённым z
и `maximum(expm1(z),0)`.
