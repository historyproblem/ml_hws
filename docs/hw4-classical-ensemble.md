## Зачем следующий экран

LightGBM, компактные признаки с контекстом, давность train и регуляризованная
ID-ветка ещё не измерялись. Нужны новые полезные ошибки, а затем небольшой
ансамбль. Более крупная архитектура сама по себе не повышает AP.

Данные табличные,21тыс. train-строк, история короткая. Поэтому этот экран
**CPU**,4 потока по умолчанию, даже на сервере с V100. Неиспользование GPU
здесь ожидаемо; предыдущий контроль CatBoost также CPU. Torch/CUDA менять
для этого запуска не требуется.

Один фиксированный seed42,9 вариантов:

| Вариант | Признаки и параметры | Гипотеза |
| --- | --- | --- |
| cb_reference | прежние346,500/depth5/lr.04/L2=10 | сопоставимый контроль |
| cb_compact |96: точные прежние24 static/calendar/burden +72context; те же параметры | меньше шумных факторов |
| cb_regularized |346,depth4/lr.025/L2=20,до1600 | более плавное ранжирование |
| cb_site |347,дополнительный categorical site_id,500/depth5/lr.04/L2=30 | повторяемые площадки со строгой регуляризацией |
| cb_recency |346,параметры контроля,веса давности half-life4 квартала | временной дрейф |
| cb_relative |354,параметры контроля | собственная нагрузка относительно area/area×risk |
| lgb_small |346,15leaves,minleaf120,lr.025,L2=10,до1600 | другое разбиение деревьев |
| lgb_medium |346,31leaves,minleaf80,lr.025,L2=15,до1600 | более гибкая модель с регуляризацией |
| et_compact |96,700 деревьев,minleaf15,maxfeatures.7 | разнообразие ошибок без бустинга |

Две LightGBM используют subsample.8/freq1 и colsample.8. У всех моделей
обычная бинарная loss, без автоматических class weights. cb_site меняет и ID,
и L2: его результат не следует интерпретировать как чистый эффект только ID.
Восемь relative-признаков — разность и own/(1+context) для history/last-routine
burden против area/area×risk365d routine code load. Missing остаётся missing.

## Временной протокол

Внешние кварталы остаются **2023Q3/2023Q4/2024Q1**; обучение строго раньше
соответствующего квартала. Последние2024Q2/Q3 отбрасываются сразу после
чтения train, до построения признаков/выбора/оценки. Test не оценивается,
test-refit и submissionCSV на этом этапе не создаются.

Для cb_regularized/lgb_small/lgb_medium число деревьев выбирается на
предыдущем внутреннем квартале по sklearn Average Precision, сетка50,100,…1600.
Затем модель заново обучается на всём раннем outer-train с выбранным числом.
Остальные варианты имеют фиксированное число деревьев. Полный экран:
27 внешних +9 внутренних fit. При импорте готового контроля —33 новых fit.
Словари LightGBM/one-hot ExtraTrees и импутация оцениваются только на fit.
CatBoost сохраняет родные numericNaN, как исходный контроль.

Сравнение включает AP каждого квартала, равновесный meanAP, ROC AUC, logloss,
precision/recall верхних5/10/20%, warm/cold и burden-срезы. В test94.83%
площадок знакомы; в dev79.45/84.53/90.09%, поэтому ID-ветку особенно важно
проверять отдельно по warm/cold. Low-burden диагностика не используется
как основание подбирать специального эксперта на тех же ошибках.

Для каждого кандидата заранее зафиксированы две смеси с CB:50/50 вероятностей
и50/50 percentile-ranks внутри квартала. Веса не подбираются; stacking нет.
Таблица выводит nominal95% paired site-bootstrapCI,1000 выборок,seed20261118;
общие веса площадки во всех кварталах и моделях. Ранги — оценки риска,
не калиброванные вероятности; logloss ранговой смеси только диагностический.
CI не учитывают многократный выбор на уже использованном dev.

## Запуск на сервере

Для прежнего checkout `~/ml_hws_hw4` с CSV в `data/`:

```bash
cd ~/ml_hws_hw4
source .venv/bin/activate
git fetch origin
git merge --ff-only origin/codex/hw4-transformers
python -m pip install -r configs/hw4-classical-requirements.txt
python scripts/test_hw4.py
mkdir -p logs
nohup bash scripts/run_hw4_classical_server.sh analysis/hw4-classical-01 data \
  > logs/hw4-classical-01.log 2>&1 &
tail -f logs/hw4-classical-01.log
```

`Ctrl-C` останавливает только просмотр tail. В конце появятся summary и
`event=complete`. Для разбора вернуть **analysis/hw4-classical-01/return_results.tar.gz**.
Он содержит протокол, все dev-прогнозы, фолдовые метрики и фиксированные смеси.
Веса остаются в job-подпапках на сервере. ExtraTrees обучается параллельно,
а прогноз считает одним потоком для точного повторения суммирования деревьев. Kaggle-отправок код не выполняет.

Повторная та же команда использует `--resume`: завершённые job пропускаются
только при совпадении SHA исходников/данных/артефактов, config и версий.
Кэш признаков также проверяется. Изменённый эксперимент требует новой --out.
Внутренний незавершённый job может переобучаться; завершённые не повторяются.

Если на сервере уже есть старые OOF context-CB, можно избежать его повторного
обучения, передав исходный predictions.csv plus_context/seed42:

```bash
python -u scripts/run_hw4_classical.py --raw data \
  --out analysis/hw4-classical-cached-01 --resume \
  --reference-oof /path/to/extensions_screen/predictions.csv
```

Для smoke: `--smoke --bootstrap 10 --quarters 2023-07-01` и новая --out.
Он использует48 train-строк каждого квартала и5 деревьев; AP из smoke
не является измерением качества. Для CPU-локального теста нужен LightGBM
с рабочей OpenMP runtime. На проверенном Mac существующая runtime лежит
в `.venv/lib/python3.12/site-packages/torch/lib`; серверный Linux-прогон
не требует Mac-переменных окружения.

## Решение после экрана

Сначала проверить присланные SHA/ID/AP и структуру ошибок, затем подтвердить
максимум две полезные ветки seed17/2026 и добавить лучшие из уже готовых
MLP/VisitTF-прогнозов. Повторная валидация тех же dev — проверка устойчивости,
не новый holdout. После фиксации состава/весов ансамбля отдельно открыть
2024Q2/Q3, выполнить final refit и подготовить два осмысленных submission.
Выбор по одной только Public-таблице или обещание топ-10 преждевременны.
